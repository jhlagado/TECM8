# TecMate Profile Preprocessor Contract

TecMate profiles are optional project shapers. They sit above the assembler and
generate ordinary AZM-compatible source, tables, labels, includes, resource
data, and metadata. They do not replace the assembler and they do not define the
core programming model for every TecMate project.

The general assembler path must remain valid:

```text
hand-written AZM/Z80 source
  -> AZM or TecMate assembler
  -> binary, map, symbols, metadata
```

A profile adds structure before that same assembler path:

```text
profile source
  -> generated AZM/Z80 source and resources
  -> AZM or TecMate assembler
  -> binary, map, symbols, metadata
```

That means profile-generated programs, monitor code, ROM tools, diagnostics,
utilities, and hand-written applications all share the same final assembly
language boundary.

## Non-Negotiables

- A profile must emit inspectable assembly that can be traced back to the
  profile source.
- A profile must not require a hidden bytecode interpreter for ordinary
  behaviour.
- Behaviour routines should be real Z80 unless a later measured design proves a
  smaller interpreted form is worth the cost.
- Profile output must be callable through the same TecMate BIOS, shell, VDU,
  input, TEC-FS, and debugger contracts used by hand-written programs.
- Generated labels and tables must be stable enough for Debug80 maps and source
  debugging to remain useful.
- Profile metadata must say what was generated: profile type, entry point,
  required display/input profile, storage dependencies, and target bank or load
  address.

## First Profile Shape

The first useful profile is likely game-oriented because games stress the
display, input, timing, resource, and debugging surfaces. That does not make
TecMate a game-only system. The game profile is a proving case for the broader
interactive-program model.

The first profile should be able to describe:

- project name and output artifact
- required display and input profile
- resource files
- actors, rooms, sprites, maps, and other game-specific records
- state record sizes
- routine slots such as `Actor_Init`, `Actor_Update`, `Actor_Touch`, and
  `Room_Enter`
- exported entry point
- TEC-FS metadata for the produced program

The preprocessor should lower those declarations to constants, tables, labels,
resource blobs, and includes. User behaviour should remain in ordinary assembly
files.

## Generated Artifact Layout

A profile build should produce a small, predictable folder of generated files.
The exact host paths can change, but the roles should not:

```text
project/
  main.asm              human-owned behaviour code
  profile.tm8p          human-owned profile declarations
  generated/
    profile.generated.asm
    profile.tables.asm
    profile.resources.asm
    profile.metadata.asm
    profile.manifest.json
```

`profile.generated.asm` is the entry file emitted by the preprocessor. It
should include the generated tables, generated resources, generated metadata,
and the user's ordinary assembly files. This keeps the final assembler input
plain and inspectable:

```text
profile.generated.asm
  -> profile.tables.asm
  -> profile.resources.asm
  -> profile.metadata.asm
  -> main.asm
```

Generated labels should use stable, profile-owned prefixes so that user labels
do not collide with generated ones. For the first game profile, examples are
`GameProfile_`, `ActorType_`, `Room_`, `Sprite_`, and `Resource_`.

The manifest is for host tools and debugging. It should record:

- source profile path, stored as a project-relative or logical path
- generated assembly paths, stored as project-relative or logical paths
- user assembly includes, stored as project-relative or logical paths
- resource inputs and generated labels, stored as project-relative or logical
  paths
- exported entry point
- target bank or load address
- required display/input/storage profiles
- generated byte counts where known
- byte-origin ranges for generated structure, user behaviour code, and resource
  blobs where the assembler listing or map can support them

The manifest is not the runtime format. It is a build-side explanation of how
the profile became ordinary assembly and then a binary. It must not contain
absolute host paths such as `/Users/...`; generated comments should use the same
project-relative or logical path convention.

## Inspectability Rules

Profile output must be easy to audit when something goes wrong.

- Generated assembly should be checked into examples only when it is useful as a
  reference; normal project builds may regenerate it.
- Generated files must start with a comment naming the profile source and the
  generator version, using project-relative or logical paths.
- Generated tables should use one label per logical record where practical.
- Generated binary blobs should have nearby labels and byte counts.
- The build should preserve source-map or listing information for both generated
  files and user assembly files.
- The build should emit byte-origin ranges where practical, so generated
  structure, user behaviour code, and resource blobs can be separated during
  size review.
- A user should be able to open the generated entry file and see the final
  include order.
- When byte-origin ranges are unavailable, the manifest must say so rather than
  implying exact ownership from a non-exclusive source map.

## Out Of Scope For The First Version

- a general scripting language
- expression compilation
- automatic dependency graphs between all fields
- object inheritance
- dynamic event dispatch as the default model
- an opaque runtime that hides the generated assembly

Those ideas can be revisited only after the shell, editor, assembler, runner,
VDU/input services, and TEC-FS project storage are useful in their smaller form.
